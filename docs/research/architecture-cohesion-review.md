# Architecture cohesion review

Date: 2026-10-02. This read-only review covers the current specifications, recorded results and retained prototype source. No builds were rerun. The original implementers were unavailable. Comments about their experience come from their written assessments and code. They do not come from a new interview or personal implementation experience.

## Overall judgment

The architecture is coherent enough to assemble a narrow reusable core. Evidence supports the central design: one resource definition supplies shared operations and reactive behavior. Actions and events are supporting values. ROM owns infrastructure contracts; providers stay behind adapters.

Composition is now the main risk, rather than the feasibility of each mechanism. The experiments deliberately use different representations and ownership models. Their separate guarantees do not establish a combined guarantee. [Recorded evidence](prototype-results.md), [adapter evidence](capability-prototype-results.md).

The owner's clarified transport split fits: **core owns the generic transport-facing semantic contract; HTTP is an extension implementing it**. The current boundary specification already requires transport independence, equivalent mutation semantics and descriptor-derived endpoints, but does not yet spell out that complete transport contract. It should cover operation discovery, input/presence decoding, trusted actor context, structured outcomes and subscription lifecycle without importing HTTP status codes or server types into domain semantics. This is a review recommendation, not a specification edit. [Boundary requirements](../../openspec/changes/establish-rom/specs/boundary-adapters/spec.md).

## What fits well

- **One descriptor and one mutation boundary remove real coordination work.** The library example adds a resource, custom function and live query without a repository or broadcaster. Runtime validation, authorization, commit and invalidation share one path. This is stronger evidence than a short macro example alone. [Application source](https://github.com/pmikstacki/ROM/blob/prototype/library-slice/prototypes/library-slice/examples/app.rs), [implementation assessment](https://github.com/pmikstacki/ROM/blob/prototype/library-slice/prototypes/library-slice/ASSESSMENT.md).
- **Capabilities are semantic rather than vendor-shaped.** The persistence prototype exposes conditional commit, durable receipt resolution and opaque journal continuation, and the same application ran on SQLite and redb. Its core trait contains no driver transaction. This preserves backend independence without pretending every backend supplies every guarantee. [Storage contract](https://github.com/pmikstacki/ROM/blob/prototype/persistence-adapters/prototypes/persistence-adapters/core/src/lib.rs), [executed limits](capability-prototype-results.md).
- **Execution, durability and observation have distinct owners.** Tokio/Rayon execute work; actual work owns permits; persistence determines whether an operation committed; live snapshots coalesce current state while the journal preserves history. These boundaries address demonstrated cancellation and stale-delivery bugs. [Execution requirements](../../openspec/changes/establish-rom/specs/execution-engine/spec.md), [execution/live-query findings](prototype-results.md).
- **Derive plus fluent composition is a sensible split.** Derive produces structural bindings; startup checks composition; the runtime decides dynamic permissions and conflicts. Generated code should call those shared contracts. The trials support useful source-local errors without requiring macro-only resource definitions. [Authoring trials](authoring-crate-trials.md).

## Where the parts still do not meet

| Gap | Concrete evidence | Why it matters |
| --- | --- | --- |
| Authoring and runtime use different interfaces | The library example mutates `Value` with `data["done"]`, queries `"done"` and invokes `"complete"`; the derive trial does not supply this runtime's typed operations. | The intended author experience remains unproved until one downstream crate uses the combined API without repeated fields or JSON business code. |
| Live reads still rely on local storage ownership | The library imports rusqlite directly and refreshes stale snapshots under its state lock. The adapter-neutral `Storage` trait offers load/commit/receipt/journal, but no query snapshot operation. | Replacing the database can remove the lock that currently makes snapshot registration, data freshness and policy checks coherent. A capability flag alone does not provide a read-consistency protocol. |
| Resource commit and external work are separate seams | Persistence `Transition` carries state and events; it has no effect intentions. Notification dispatch owns a separate `Intent`/`Outbox` contract. | Joining them must commit intentions with state/events/receipts or a crash can lose or invent external work. Atomicity cannot come from calling two APIs consecutively. |
| Admission, disclosure and lifecycle guarantees are distributed across experiments | Cache tests supervise jobs and recheck authorization; library tests repair stale live delivery; execution tests drain abandoned CPU jobs. | The integrated runtime must retain all three behaviors through cancellation, shutdown and uncertain commits. Each subsystem passing alone is insufficient. |

Sources: [library implementation](https://github.com/pmikstacki/ROM/blob/prototype/library-slice/prototypes/library-slice/src/lib.rs), [persistence implementation](https://github.com/pmikstacki/ROM/blob/prototype/persistence-adapters/prototypes/persistence-adapters/core/src/lib.rs), [notification contract](https://github.com/pmikstacki/ROM/blob/prototype/notification-channels/prototypes/notification-channels/core/src/lib.rs), [cache results](cache-prototype-results.md).

One especially important composition question is **policy and read freshness across writers**. The repaired live-read implementation compares local generation/policy epochs. It reloads under a local lock. This supports the tested single-owner process. The persistence experiments separately prove independent database writers can arbitrate revisions, but do not prove another process refreshes local live queries or policy-dependent cache disclosure. Explicitly scope the first integrated milestone to one runtime owning writes, or implement an authoritative cross-process generation/read contract before making broader claims. [Stale-buffer implementation](https://github.com/pmikstacki/ROM/blob/prototype/library-slice/prototypes/library-slice/src/lib.rs), [independent-writer evidence and limits](capability-prototype-results.md).

## What working on it appears to be like

The retained implementer assessment identifies a useful division of labor: applications write declarations and ordinary business functions; framework maintainers absorb transaction, authorization, registration and subscription complexity. The example confirms the application plumbing reduction. It also exposes the unfinished ergonomics: string field/action names, JSON state mutation, positional revision arguments and runtime-only value errors. The authoring trials improve these separately, but no human walkthrough has tested the joined API. [Assessment](https://github.com/pmikstacki/ROM/blob/prototype/library-slice/prototypes/library-slice/ASSESSMENT.md), [example](https://github.com/pmikstacki/ROM/blob/prototype/library-slice/prototypes/library-slice/examples/app.rs), [readiness review](core-implementation-readiness.md).

The builder trial gives a specific warning. Typestate setters change the builder type, so naive conditional reassignment fails. ROM can offer helpers or accept values computed before construction; exposing generated state types to ordinary authors would make fluent authoring harder. Diagnostic source spans and renamed/reexported dependency behavior deserve acceptance checks alongside correctness. [Trial results](authoring-crate-trials.md).

The original assessments do not justify calling the framework pleasant yet. They establish that a small application can avoid repeated plumbing and that maintainers encountered tractable but substantive correctness issues. The stale authorization bug and reaction-ID bug show why a central runtime is valuable, while also showing why generated convenience cannot substitute for invariant testing. [Recorded regressions](prototype-results.md).

## Technology choices and limits

There is no evidence here that Rust, Tokio or Rayon is the wrong foundation. The execution probe directly rejects caller-owned capacity, while the specification sensibly leaves tiny validators synchronous. The mistake would be treating a runtime choice as the durability or supervision design. [Execution evidence](prototype-results.md), [execution contract](../../openspec/changes/establish-rom/specs/execution-engine/spec.md).

SQLite and JSON were productive experimental tools; promoting their serialization and global-lock assumptions unchanged would undermine the intended typed, adapter-independent contract. Likewise, Moka/quick_cache should remain replaceable implementation details: warm replay improvements do not establish acceptable unique-command overhead. Salsa is a candidate for costly pure derived reads only after ROM owns projection, policy dependencies and lifecycle; a second hand-maintained schema would violate the single-declaration premise. [Library assessment](https://github.com/pmikstacki/ROM/blob/prototype/library-slice/prototypes/library-slice/ASSESSMENT.md), [cache/Salsa results](cache-prototype-results.md).

The next phase should choose one narrow query/type subset and a reference host topology, then integrate. More independent cache/provider prototypes would currently reduce less uncertainty than that work. This does not select a production database. [Open decisions](core-implementation-readiness.md).

## Smallest useful integrated acceptance scenario

Build one packaged downstream application defining a typed `Task` resource with owner, title and done fields, one ordinary `complete` action and a boolean live query. Use one runtime owning writes, one configured persistence adapter and conservative full-result recomputation. Omit completed caches, Salsa and blob coordination from this first test.

1. Derive and fluent registration produce typed fields/action inputs and the same normalized descriptor used by embedded calls and the generic transport contract. Enable HTTP as a thin extension and run the same action/conflict/presence assertions through both entry points.
2. Subscribe as an authorized actor, run `complete`, and observe the task disappear from the open-task result. No application repository, route or invalidation handler is allowed.
3. Gate an admitted operation, cancel its first caller, and retry the same durable identity. Inject a lost response after commit. Assert one revision/event/outcome and no early release of the work permit; shutdown must drain the retained operation.
4. Buffer a result, revoke ownership or policy before delivery, and assert neither the live result nor a retried outcome discloses data forbidden by current authorization.
5. Add a second resource solely by declaration/registration. Unsupported adapter requirements and an intentional invalid field/action input must fail at the appropriate source/startup/runtime boundary with resource context.

That is the minimum evidence that the central authoring/runtime/transport story composes. Immediately afterward, extend the same scenario with one durable notification intention in the mutation transaction, then force worker loss and verify stable delivery identity on recovery. This second gate closes the highest-risk cross-capability seam; it must precede claims that external effects are integrated. Adapter substitution should then run these same public conformance cases without changing resource declarations. These are proposed acceptance tests, not existing guarantees.
