## Minor: clarify key reuse after an inconclusive verification

The recovery design, docs/superpowers/specs/2026-10-03-operator-recovery-design.md:198,
says a later verification attempt uses a new operator request key.
The accepted real CLI journey intentionally repeats the same exact request after Unresolved,
then obtains Accepted and an exact terminal receipt replay.

Runtime stores no transition or receipt for Unresolved. Repeating unchanged input under that unused identity
therefore performs another read-only verification and can safely produce the first terminal receipt.
The implementation and CLI test agree, but the design instruction describes only the new-key path.

Clarify that an unchanged inconclusive request can be repeated before a terminal receipt exists.
Changed input or a separate intent needs a new key. Exact retries of an accepted operation retain the original key.
Do not add identity reservation or another history mechanism merely to enforce the older instruction.

## Spec review

Channel::delivery_profile returns a typed ChannelRegistration containing the channel handle.
Builder::channel delegates to channel_with with AtLeastOnce, preserving existing call sites.
The optional trusted verifier and timeout stay on the declaration, without an unrelated string registry.
DeliveryReconciliation and DeliveryVerification have no Deserialize implementation.
The public request still carries only a bounded opaque lookup reference, not a trusted verdict.

Notification materialization persists the declared profile without changing delivery identity construction.
One matcher covers definition name/version, service key and profile for ordinary delivery and controls.
A changed retained profile prevents sending or control reinterpretation.
Legacy AtLeastOnce work remains compatible with the ordinary channel registration.
No persisted field, native/archive format or query encoding version changes in this patch.

Controls prepare under the core gate, check operator/current actor authority, snapshot bounds,
retry floors, exact saved receipt, work version and leased/done state.
Notification preparation checks the recorded service and source Resource disclosure authority.
Active leases are refused before verifier invocation.
Existing action receipt resolution remains shared and unchanged.

Provider verification starts after the gate and all synchronous storage reads have ended.
The callback uses the existing supervised I/O job and shared delivery callback supervisor.
The job retains its Runtime, ownership and I/O permit when the caller stops waiting.
Timeout aborts and joins the cooperative async task; a late or invalid value cannot become trusted evidence.
The public registration docs and operator guide explicitly exclude preemption of blocking/non-yielding Rust code.

After verification, Runtime reacquires the gate and repeats current authority checks.
An exact concurrent saved receipt is authorized and validated before stale CAS.
Otherwise the original work version, frozen declaration and service/source authority must still match.
Terminal evidence passes the shared nonempty/1024-byte identifier validator.
Accepted completes without sending; NotAccepted uses the existing lifecycle budgets.
Unresolved, timeout, panic or malformed evidence yields no transition or receipt.
Post-commit receipt validation and disclosure failure retain the existing Unknown contract.
Public responses echo caller operation identity while excluding trusted provider evidence and frozen payloads.
