# Disposable configuration loader trials

Date: 2026-10-02. Branch: `codex/prototype-configuration-trials`, based on `main` commit `e3e6a37`. **Executable experiment, not a production implementation or dependency adoption.** The source is in [prototypes/configuration-trials](../../prototypes/configuration-trials/README.md); keep it off main unless deliberately retaining research artifacts.

## Question and answer

Can current config-rs and Figment supply layered values to the **same accepted Resource definitions** while ROM owns validation, source authority, ownership, revisions and reload publication?

**Yes for this bounded in-memory contract, with either loader.** Both pass identical wrapper checks for `User`, `AppSettings` and `IdentityProvider`. Neither removes the need for ROM's control plane. The surprising counterexample is provenance: config's `get::<config::Value>()` returns a deserialized value without origin, although `Source::collect()` retains it. Figment's provider metadata and contextual extraction errors are easier to inspect. Both libraries' raw errors can contain supplied secret-like strings.

**Recommendation:** retain config-rs as the first narrow JSON/TOML input adapter, with explicit features, an internal provenance sidecar and literal Resource identities kept outside its path namespace. Do not expose either library's merge/profile API as the Resource contract. Figment is a credible replacement if provider-native diagnostic attribution becomes a major requirement; the trial does not establish enough benefit to make its profile/merge vocabulary a ROM dependency. There is no throughput result or decisive code-size win. Descriptor-aware admission and reconciliation dominate the implementation, so a plain parser-only adapter remains a viable later simplification.

This recommendation follows [the existing provider research](configuration-provider-research.md), [Resource configuration contract](configuration-resource-contract.md), [Beskid lessons](configuration-beskid-lessons.md), and the accepted premise in [OpenSpec](../../openspec/changes/establish-rom/specs/resource-model/spec.md). Sources cannot register a kind or supply a schema. The prototype's small compiled field registry stands in for ROM's future accepted definitions; it is not integration with a production core that already exists.

## Observed library behavior

All observations in this table are executable assertions in [loader_behavior.rs](../../prototypes/configuration-trials/tests/loader_behavior.rs), rather than promises derived solely from documentation.

| Trial | Observed result | Implication |
| --- | --- | --- |
| Nested maps, arrays, omission and null | Both recursively overlay objects, replace arrays, preserve omitted lower fields, and retain explicit JSON null. An empty overlay deletes nothing. | Null is a value; lifecycle deletion needs a separate operation. |
| Defaults → two real files → operator override | Both select the operator title and inherit a lower note. TOML and JSON loaders agree on this subset. | Host-defined ordering is feasible without implicit directory discovery. |
| Figment alternative modes | `join` keeps prior scalar/array values; `admerge` concatenates arrays; global-profile values defeat later default-profile values. | Use one intentionally selected mode/profile; do not let providers select public precedence. |
| Invalid shadowed input | A wrong-type lower `enabled` value disappears beneath a valid boolean in both loaders. | Successful final extraction does not validate every contribution. ROM admission runs first. |
| config provenance | Named custom sources and a real file preserve winning origins via `collect`; generic `get::<Value>` loses origin. Type errors retain key/origin. | Capture provenance before generic deserialization; do not reconstruct it later. |
| Figment provenance | Winning JSON provider metadata and error field path remain inspectable, including a real file path. | Better built-in diagnostic ergonomics; not a full overridden-value history. |
| Invalid-value disclosure | Both raw type-error strings contain the supplied `sensitive-marker`. | Map errors into protected structured codes/context; avoid forwarding library error strings to Studio or logs. |
| Dotted/bracket Resource ID | A top-level `alice.example[0]` key is interpreted as a path by config; Figment preserves the literal key. Nested map keys survive the tested config load. | The wrapper keeps Resource IDs in a separate map and merges each Resource's fields independently. |
| Malformed JSON | Both reject it. | Parsing failure remains distinct from an empty complete source. |

## ROM-owned wrapper results

Every row below belongs to [the disposable wrapper](../../prototypes/configuration-trials/src/lib.rs), not config-rs or Figment. The wrapper stages a complete candidate and publishes through one mutable in-memory runtime. This is a local serialization point, not a database transaction or multi-host protocol.

| Boundary | Positive and negative evidence |
| --- | --- |
| One Resource model | The same compiled registry, value validator, revision computation and read path handle all three kinds. A dotted User ID round-trips unchanged. Unknown kinds, fields and malformed typed values fail. |
| Authority before precedence | Host grants select source identity, allowed kinds, trust-management permission, precedence and overlay capability. A high-priority project source cannot add an issuer or overwrite another owner's settings. Documents cannot supply their own grant or schema. |
| Partial values | Missing inherits, nullable note can explicitly clear to null, nonnullable title rejects null, audience arrays replace. Bad lower input is rejected even beneath a valid Studio winner. |
| Explicit ownership | Named Studio overlay survives lower deployment reload. Removing that overlay reveals the updated inherited value, without materializing defaults into the overlay. Winner source and source sequence are inspectable. |
| Delete versus failure | An explicit tombstone deletes a Resource owned solely by that source. A source cannot delete another owner's Resource. A failed fetch retains active state and is never treated as an empty source. |
| Environment | ROM-owned allowlist over a captured map ignores unrelated variables, rejects unknown names and case aliases, preserves `false` as a declared string and preserves empty strings. No process environment is mutated. |
| Bootstrap | Unknown source cannot begin; an empty initial snapshot cannot activate; a host-granted seed installs all three kinds; bootstrap authority ends after first publication. This is **not** a real first-admin enrollment or durable recovery test. |
| Invalid reload | A candidate containing both a valid edit and an invalid Resource publishes neither. Generation and all Resource values remain unchanged; rejection is visible. Public error codes contain no supplied input values. |
| Freshness | Active reads are rejected at a logical expiry boundary even after a rejected reload. The fixed test deadline is not a selected production freshness policy. |
| Late completion | Two real channel-gated worker threads complete in reverse request order. The old completion cannot overwrite the new one. A newer failed fetch also invalidates an older pending candidate. |
| Concurrent Studio mutation | A prepared deployment candidate conflicts after an intervening Studio edit. Reacquiring/repreparing preserves the Studio overlay. |
| No-op and ambiguity | Identical source replay keeps active generation and Resource revision, while source sequence advances. Duplicate envelope identity, ambiguous values+delete, unknown envelope members and equal-priority sources fail. |

The small per-loader bridge is similar in size: config needs a builder/add-source/build/extract chain; Figment needs merge/extract. The prototype serializes values back through JSON for this comparison and is intentionally inefficient. Production adapters should avoid that round trip and preserve loader provenance before conversion. Changing a kind adds fields to the shared registry rather than another repository/action path. The larger engineering cost lies in source lifecycle, authorization, validation, ownership and recovery.

## Critique and limits

The ownership fixture allows explicit overlays and uses whole-source replacement snapshots. It conservatively rejects deletion when any field has another owner. It does not implement field-specific grants, writeback, partial incremental source patches, keyed-array merging or cross-tenant scope. The model records winning fields and retains private source layers; it does not provide a complete authorized provenance/history projection. Empty-source completeness is asserted by the caller; real providers need an authenticated snapshot manifest and source revision/digest.

Generation checks are conservative: any intervening publication conflicts, even for disjoint Resources. This makes the safety property easy to exercise but can cause unnecessary retries. Sequence numbers are process-local. Identical accepted source content advances its provenance sequence without advancing generation. Production needs a deliberate contract for source freshness, Resource revision and active generation, including restart persistence. Deletion/recreation revision continuity, overflow bounds and expired-state renewal are not implemented.

The host grant fixture is trusted in-process input, not cryptographic authentication or a policy engine. The `https://` issuer and `secret://` reference checks are illustrative descriptor validation, not URL validation, resolver authorization or issuer discovery. No real secret value is fetched. Debug representations are not hardened for protected data. Error codes are safe in the exercised cases but lack production field/location detail. Full JSON duplicate-member detection, nesting/size limits and Unicode normalization remain untested.

There is no durable Resource journal, crash recovery, external adapter activation, connection draining, file watcher/writeback, multi-file generation coherence, HTTP/Studio integration, lease renewal, key rotation or multi-host convergence. Async workers simulate arrival order; neither crate's async provider API nor actual remote transport was benchmarked. This trial does not merge the separate authoring/library prototype or establish a production public API.

## Unsettled identity, bootstrap, tenancy and secrets

This follow-up reuses [auth architecture](auth-architecture.md) and [the configuration contract](configuration-resource-contract.md), with fresh first-party source checks. These are design recommendations, explicitly **not new executable auth evidence**. “Discussed/open” describes a decision already identified in those documents; “unprototyped here” identifies work this crate trial did not perform.

| Topic and current evidence | Options and critique | Recommended smallest next step / owner decision |
| --- | --- | --- |
| **User ↔ external identity linking: discussed/open; unprototyped here** | One User with provider bindings avoids treating each login as a new person. A separate managed binding can also be a Resource if it needs its own policy/history. Email matching is not an identity proof. Automated just-in-time linking broadens takeover risk and needs explicit policy. | Bind a host-approved authority namespace and verified opaque subject to one User; enforce uniqueness through storage. Use explicit admin-approved linking initially. Owner must decide self-service linking, account merge, invitation/JIT provisioning and issuer migration. No separate mandatory user store. |
| **Human/service distinction: discussed/open; unprototyped here** | A shared token subject namespace can confuse a machine client with a human. Inferring kind solely from `sub` is insufficient. | Adapter profile must supply verified principal kind and optional client identity. Owner chooses first concrete provider/profile and whether service identities need managed Resource records. |
| **First admin and recovery: discussed/open; toy bootstrap guard tested** | Public first-caller-wins is unsafe. Host-provisioned subject binding is simple; one-time recovery token needs storage, expiry, replay defense and audit. Local offline recovery avoids public takeover but adds an operational procedure. | Explicit host-provisioned initial administrator binding; consume a durable bootstrap capability after successful ordinary Resource actions. No internet enrollment endpoint initially. Owner chooses recovery operators, recovery credential location and audit procedure. The in-memory `sealed` boolean is not sufficient across restart. |
| **Tenant boundary: discussed/open; unprototyped here** | Per-tenant runtime/storage gives a clearer initial boundary; shared storage is economical but every Resource ID, query, event, idempotency key and membership decision must carry tenant scope. An arbitrary token tenant claim cannot choose scope. | First milestone supports a declared single tenant and rejects cross-tenant context. If immediate multi-tenancy is required, owner chooses per-tenant stores versus shared storage, stable membership authority and cross-tenant administration before broad queries ship. |
| **User disable and revocation freshness: discussed/open; only config deadline tested** | Local User disable, provider token revocation, issuer/key withdrawal and session logout are different events. JWT verification alone does not observe remote revocation; introspection can, subject to cache windows and availability. | Check current User enabled state and current policy version on mutations, reads, cached receipt access and stream delivery. Bound actor/key/policy validity, fail after expiry, invalidate long-lived subscriptions. Owner must choose numeric outage/revocation tolerances and whether the first provider supports introspection. |
| **Secret references: discussed/open; reference syntax and safe error codes tested** | Pinned versions improve reproducibility; latest-version references ease rotation but need freshness/reconciliation. Reference paths can themselves be sensitive. | Store typed resolver ID, scoped identifier and explicit version/follow policy in configuration Resources. Fetch bytes only within the authorized adapter lifecycle. Owner selects first resolver and who may read/change references. No generic Studio “reveal secret” action initially. |
| **Rotation and redaction: discussed/open; real rotation unprototyped here** | Swapping a local snapshot does not prove a remote service accepted a replacement credential. Keeping old material indefinitely can defeat emergency revocation. Library diagnostics can disclose invalid values, as tested. | Prepare replacement handles, record desired versus active version, publish then drain where supported; model failure/pending honestly. Use a separate emergency-revocation path with bounded denial. Test raw-value absence in events, receipts, errors and traces. Owner decides overlap windows, failure behavior and audit retention. |

Identity evidence: OIDC guarantees issuer+subject stability, not email uniqueness, and describes pairwise subjects; ROM's binding policy is an inference from those constraints. It does not imply accepting ID tokens as API access tokens. [OIDC Core §5.7](https://openid.net/specs/openid-connect-core-1_0.html#ClaimStability), [subject types](https://openid.net/specs/openid-connect-core-1_0.html#SubjectIDTypes). OAuth security guidance explicitly discusses confusing client and resource-owner subjects; provider profiles must distinguish them. [RFC 9700 §4.15](https://www.rfc-editor.org/rfc/rfc9700.html#section-4.15).

Freshness evidence: introspection caches introduce a revocation window; RFC 7662 requires choosing a cache duration appropriate to sensitivity, and expiry bounds cached use. It supplies no universal safe ROM timeout. [RFC 7662 §4](https://www.rfc-editor.org/rfc/rfc7662.html#section-4). Tenant isolation, first-admin enrollment and local User-disable semantics are ROM product decisions; these OAuth/OIDC documents do not settle them.

Secret evidence: 1Password supports secret references instead of embedding values. Vault KV v2 exposes versioned reads, with latest-version selection when no version is specified, and version-conditional writes. Neither proves that an external client was reconfigured or that a rollback removed external effects. [1Password references](https://www.1password.dev/cli/secret-references), [Vault KV v2](https://developer.hashicorp.com/vault/api-docs/secret/kv/kv-v2).

## Minimal next milestone and decision inventory

Build one durable vertical slice: accepted Resource definitions → authorized source import → ordinary expected-revision Resource actions/journal → prepared runtime generation → protected read. Use one deployment file, one explicit writable overlay, one configured identity provider profile, single-tenant scope, and secret references to one host-approved resolver. Demonstrate restart after a committed-but-not-active change, source failure, conflicting Studio edit, User disable, bounded subscription revocation and credential rotation failure. Keep bootstrap/recovery host-controlled. Use the existing host authorizer seam with a small Rust policy implementation; **this report does not select Cedar, Casbin or another policy engine**.

Decisions still requiring the owner: concrete provider/access-token profile; browser login scope; linking and provisioning policy; first-admin/recovery operators; immediate multi-tenancy requirement; freshness and outage limits; read-only versus writable source ownership; resolver/version/rotation policy; permitted overlay fields and restart-only settings. The tests support mechanisms but do not choose these product policies.

Technical work not closed by discussion or this prototype: canonical Resource registration/codec integration; durable bootstrap receipts; transactional identity-binding uniqueness; full field-level authorization/provenance projection; query/event/receipt tenant isolation; live verifier interoperability; bounded remote acquisition; secret-resolution and rotation crash probes; coordinated multi-Resource publication; external activation reconciliation; production error redaction and input bounds. Each remains a separate acceptance task, not an implied capability of a configuration crate.
