# Disposable provider-neutral authentication probe

Date: 2026-10-02. Branch: `codex/prototype-auth-provider-probe`, based on `main` commit `e3e6a37`. **Disposable executable evidence; no production authentication, login service or policy-engine adoption.** Source: [auth-provider-probe](https://github.com/pmikstacki/ROM/tree/codex/prototype-auth-provider-probe/prototypes/auth-provider-probe/README.md).

## Question and recommendation

Can two materially different verification profiles construct the same trusted actor, while User, IdentityProvider configuration and settings remain ordinary Resources and core authorization stays independent of HTTP/crypto/provider drivers?

**Yes for the bounded profiles exercised here.** A real RSA-signed JWT adapter and a real loopback HTTP introspection adapter feed one dependency-free core crate. The core explicitly links verified human identities to User Resources, applies current User-enabled and host-policy checks before every demonstrated operation, and denies revoked/disabled retries before returning an idempotency receipt. The second adapter creates service identities, which remain distinct from human identities even when subjects match.

Recommendation: use an explicit verifier → trusted actor → shared Resource authorizer boundary. Keep the first host policy in Rust; defer a policy engine until concrete policy-authoring requirements justify an executable comparison. Treat the two profiles below as testable adapter contracts, not interchangeable promises of arbitrary IdP compatibility. The proposed production interfaces in [auth architecture](auth-architecture.md) and [OpenSpec](../../openspec/changes/design-provider-neutral-auth/specs/provider-neutral-auth/spec.md) remain broader than this prototype.

## Exact supported profiles

| Dimension | JWT human access-token profile | Introspection service profile |
| --- | --- | --- |
| Protocol boundary | Compact signed JWT, RS256 only, PEM public keys from one host-selected key source. | HTTP POST, form `token` and `token_type_hint=access_token`, HTTP Basic client authentication, JSON response. |
| Trusted issuer/resource | Exact configured `iss`; configured audience must occur in `aud`. Host authority namespace is separate from unverified token input. | Configured endpoint plus exact response `iss`; configured audience must occur in string/list `aud`. `active=true` alone is insufficient. |
| Profile and principal kind | Exact `typ` of `at+jwt` or `application/at+jwt`; required nonempty `sub`, `client_id`, `jti`, integer `iat` and `exp`; explicit provider extension `principal_kind=human`. | Required nonempty `sub`, matching `client_id`, `principal_kind=service`, `token_type=Bearer`; these are this provider profile's additional requirements. |
| Time | Required expiry; `nbf` when present; no future `iat`; zero leeway; maximum issued lifetime 3600 seconds. | Required expiry; `nbf`/`iat` checked when present. Actor/cache lifetime ends at the earlier of expiry or five seconds from verification. |
| Trust refresh | At most eight cached keys; at most one fetch attempt per five seconds; whole key-set replacement; key validity thirty seconds. Actor validity also ends at the earlier of token expiry/key deadline/thirty seconds. | Eight-entry cache keyed by SHA-256 of the opaque token, bounded by time and token expiry; capacity flushes the small cache. Explicit host invalidation is available. |
| Untrusted inputs | Token length ≤16 KiB; key ID ≤64 bytes; subject ≤256 bytes. Reject header key URLs, embedded JWK, unsupported critical headers and proof-bound `cnf`. | Token ≤4096 bytes, response ≤16 KiB; reject missing binding/identity evidence, proof-bound `cnf`, wrong kind/client/type. Redirects disabled; proxy discovery disabled. |
| Network behavior | Trusted key acquisition is an in-memory fixture seam; **no discovery/JWKS HTTP fetch is implemented**. | 250 ms connect / 500 ms request timeout; HTTPS required except an explicit numeric-loopback HTTP test mode. Non-success, malformed or timed-out responses fail closed. |

These are deliberately narrow **synthetic provider profiles**. `principal_kind` is a provider-specific extension, not a standard OIDC/OAuth claim. The JWT profile tests core RFC 9068 access-token checks, but does not implement JWE, HTTP challenge responses, discovery, real provider interoperability or every conforming spelling/extension. The introspection profile intentionally requires fields RFC 7662 otherwise makes optional. Unsupported proof constraints are rejected rather than silently handled as bearer tokens.

Protocol grounding: RFC 9068 specifies access-token typing, issuer/audience/signature/expiry checks and required claims. JWT BCP warns against algorithm confusion, cross-token substitution and attacker-controlled key lookup. [RFC 9068 §§2,4](https://www.rfc-editor.org/rfc/rfc9068.html#section-4), [RFC 8725](https://www.rfc-editor.org/rfc/rfc8725.html#section-3). RFC 7662 defines authenticated introspection and explains that caching creates a revocation window and cannot outlive token expiry; this trial's numeric limits are **probe choices**, not standards-mandated safe production values. [RFC 7662 §§2,4](https://www.rfc-editor.org/rfc/rfc7662.html#section-4).

## Critique and integration into the typed core

`ActorIssuer` is an explicit trusted native-host capability, not an in-process sandbox. Its constructor is public for host/adapter integration; ordinary transport payloads cannot deserialize Actor and cannot assign its private fields. Native code that controls the host can create actors and change policy. Production should make that trust boundary conspicuous and keep the capability out of request parsing code.

The core here is a small independent Resource simulator, not a second product entity engine and not integration already completed against ROM's typed-core branch. It has a fixed compiled registry and generic fields only to test policy placement. It uses one in-memory serialized mutation path; there is no durable journal, crash-safe binding uniqueness, database transaction or multi-process race. Resource creation is host bootstrap only; generic create/delete/query machinery is absent. Read-result projection is explicit; action receipts expose only revision, so replay does not require retaining a protected Resource snapshot.

Integration should replace that simulator with the typed core's accepted registry, existing action/revision transaction and event/idempotency stores. Pass immutable actor/context through the same embedded and transport entrypoints. Resolve human identity through a unique authority+subject+kind binding on a User Resource; validate current User disablement before authorization and idempotency lookup. A User profile must never substitute for verified evidence. Project only fields the current policy permits, and apply the same rule when returning cached results or delivering historical events. Keep adapter crates optional so the core dependency graph remains transport-free.

Source admission should validate IdentityProvider Resource changes under the currently trusted policy, then prepare verifier configuration before publication. **This probe does not wire the IdentityProvider Resource's `enabled` field to adapter lifecycle**: issuer disablement, key withdrawal and existing-actor invalidation need the coordinated configuration/policy-generation path. They cannot be claimed merely because a Resource patch committed. Live external keys, credential rotation and the configuration-provider prototype must be connected in the integrated milestone.

The cache methods accept a trusted host time value for deterministic boundary tests, while jsonwebtoken also uses system time for its built-in validation. Production needs one clock/freshness contract; actor snapshots pin prior evidence until their stated deadline. Key refresh is synchronous and process-local, with rate limiting but no concurrent fetch coalescing, key-source network timeout, trusted discovery, cache persistence, per-issuer fleet coordination or emergency invalidation stream. The `TrustedKeys` callback could block indefinitely if misimplemented. The HTTP probe uses a blocking client: execute it outside async runtime workers or replace it with a bounded async adapter. TLS is compiled and required by configuration outside fixtures, but TLS handshakes/certificate failure were not exercised on loopback HTTP.

No OIDC browser redirects, PKCE, session cookies, password storage, refresh-token flow, delegated human/client authority, mTLS, DPoP, JWE or generic provider-discovery support is implemented. `client_id` is validated but not carried as a separate delegated client in the actor; that remains a host-profile design task. JWT `jti` is required but is not a token-replay or revocation database. Tokens may legitimately be reused while valid. Private-key/secret memory zeroization, dependency vulnerability audit, RSA key-strength admission, complete JSON ambiguity fuzzing and timing side-channel review remain outside this disposable evidence. No performance benchmark is claimed.

## Engine, tenancy and bootstrap recommendations

**Policy engine:** plain Rust remains the smallest first milestone and is the only policy implementation executed here. It makes core ordering and error handling visible. Cedar is attractive when users need a typed policy language, but its evaluator skips individual erroring policies; a ROM adapter must inspect diagnostics and deny on errors to preserve ROM's current requirement. Casbin supports established authorization models and role relationships but does not authenticate users or replace their Resource lifecycle. Neither engine was installed or benchmarked; neither is selected by this report. [Cedar authorization semantics](https://docs.cedarpolicy.com/auth/authorization.html), [Casbin scope](https://casbin.apache.org/docs/overview/).

**Client libraries:** current oauth2 5.0.0 provides typed introspection and OAuth client flows, plus guidance to disable HTTP redirects. This probe uses a small explicit wire profile over current reqwest instead, avoiding an unused grant/login client surface. Reconsider oauth2 when a concrete integration needs token acquisition, revocation or richer response types; compare its actual feature/dependency graph then. [oauth2 documentation](https://docs.rs/oauth2/5.0.0/oauth2/). Raw JWT/HTTP library errors must remain mapped to safe errors; no credential or full claims dump belongs in generic diagnostic output.

**Tenancy:** this probe deliberately accepts only `tenant-a` and denies a different trusted context. That establishes no shared-store isolation guarantee. Prefer one explicit tenant for the first integrated milestone; if multiple tenants are required immediately, decide separate stores versus shared storage before exposing queries/cursors/history. Tenant must qualify Resource identity, binding uniqueness, policy snapshots, idempotency keys and event authorization under the chosen model. An arbitrary token tenant claim is not permission to select a tenant. This is a ROM design recommendation, not an OIDC guarantee.

**Identity and bootstrap:** preserve explicit authority-qualified User linking; never auto-merge by email. OIDC's stable issuer+subject pair motivates that rule, while different principal kinds must remain distinguishable to prevent client/resource-owner confusion. Start with host-provisioned first-admin binding and a durable one-use bootstrap receipt; do not expose first-caller-wins enrollment. The bootstrap API here is trusted in-memory fixture construction, **not** durable first-admin recovery. Owner must select real enrollment/recovery operators, approval policy, retained audit evidence and self-service linking/provisioning scope. [OIDC stable claims](https://openid.net/specs/openid-connect-core-1_0.html#ClaimStability), [OAuth client impersonation guidance](https://www.rfc-editor.org/rfc/rfc9700.html#section-4.15).

## OpenSpec evidence and remaining decisions

This supplies disposable evidence toward task **1.2** and optional adapters **3.1/3.2**, plus small executable portions of **1.4/1.5, 2.1–2.4 and 3.3**. It does not mark those production tasks complete. No OpenSpec checkboxes were changed. Exact-resource reads, profile patches, current retry checks and simulated delivery authorization are narrower than the full specification's query, deletion-retry and historical subscription requirements.

Still discussed/open: first concrete real provider pair and supported token profiles; accepted clock skew, key/actor/policy/revocation windows and outage behavior; self-service linking/JIT provisioning; first-admin/recovery procedure; immediate multi-tenancy; delegated actor/client mapping; policy authoring needs and optional engine choice; secret resolver and verifier credential rotation. Owner decisions are needed before these become fixed public contracts.

Still unprototyped here: actual provider interoperability and TLS failure; remote JWKS discovery/cache-coalescing; immutable policy-generation propagation across multiple hosts; transaction-consistent external policy data; deleted-Resource retry authorization; safe query/count/cursor/history disclosure; durable unique binding/link races and crash recovery; issuer disablement across already-issued actors; live subscription termination; secret resolution/rotation/redaction across persistent receipts and logs. The next integrated MVP should connect the existing typed Resource core and configuration-admission path, then prove restart, conflict, disablement and rotation failure without adding a second User/configuration entity system.
