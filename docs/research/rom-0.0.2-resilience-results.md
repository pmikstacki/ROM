## Native scenarios

The [new suite](../../tests/persistence/tests/studio_resilience.rs) uses real SQLite and redb databases.
Its two application Resources are `Record` and `Ledger`. Managed identity uses the existing User, IdentityProvider and IdentityLink Resources.
The tests obtain sealed OIDC evidence through `OidcIdTokenAdapter`, `ProviderActivation` and the real `IdentityGate`.
Ephemeral RSA signatures are generated by the existing shared authentication test helper.
They are not tokens acquired from an actual provider.

| Scenario | Executed cases | Assertions |
| --- | --- | --- |
| Identity changes during accepted action work | Two stores × Provider/User/link × retained/cancelled caller: 12 cases | A proposal pauses after admission. Current identity disablement completes while it waits. Capacity remains owned after cancellation. Released work cannot change the row or create another business event. The retained caller gets Denied. Replay, metadata and live disclosure are denied. Re-enabling does not revive the old actor. Reopen preserves the unchanged application row. |
| Policy reads public native Storage during a query | Two stores × reference/uniform eligibility: four child processes | Query and row/actor policies call `Storage::load` on another Resource. Each query completes with the expected row. Query permission precedes row/read authorization. A denied query field reaches no row/read callback. SQLite uses actual native candidates for the eligible request; redb retains its reference fallback. |
| Identity and historical replay through maintenance | Two stores: two cases | An owned Runtime blocks offline migration before conversion or publication. After shutdown and ownership release, schema migration preserves source bytes and identity Resources. Reopen requires explicit new proof binding in the journey. The original request replays through its recorded codec without another mutation. Current link disablement then denies receipt disclosure. |
| Strict reconciliation hold and saved operator receipt through migration | Two stores: two cases | A frozen strict delivery reaches Unknown, records a NotAccepted reconciliation receipt, then reaches a second hold. Migration preserves work identity, service, cause, payload, profile, attempts, root usage, limits, receipt and provider evidence. It changes storage generation and converted work revision. Exact replay precedes stale CAS and changes no state. Changed identity, stale new controls, late finish and Retry bypass are rejected. Backup and clean reopen retain the receipt and hold. |

The identity action cases use a fixture-controlled pause, not a timing sleep.
The release sender also runs on scope exit, so an assertion failure can release the blocking proposal.
Native query cases run in isolated child processes through the existing bounded process helper.
Its completion deadline and Drop cleanup prevent a native lock regression from leaving the suite blocked indefinitely.

The query fixture checks the actual adapter response for the declared selection mode before its Runtime query.
It does not introduce a query wrapper, alternate candidate planner or database-lock callback.
Redb's reference fallback is preserved; uniform eligibility does not claim redb acceleration.

The migration fixture uses public `migrate_from`, backup, reopen and trusted storage control ports.
Operator principal and provider evidence are explicitly synthetic trusted inputs at that port.
This scenario proves persisted control correspondence; it does not authenticate a provider or certify a provider lookup.
No direct state-blob edit, format-marker lowering or fabricated legacy wire shape is used.

## Result and corrections

No production core defect was reproduced. The new scenarios pass the existing core and native implementations.
No core, native adapter, authentication implementation or host production source changed for this subset.
The coordinator added test-only authentication/identity dependencies and refreshed the lockfile without a new resolved package version.

The first author compilation found module-path ambiguity, a shadowed helper name, storage method spelling and an enum comparison.
Those were fixture authoring corrections. They are not acceptance RED or production defects.
The first behavioral run passed identity, maintenance and all query children.
Its migration assertion incorrectly required a new claim generation for an already held record.

Source and contract review confirmed that this record had no active lease to fence during restore.
The corrected assertion preserves its claim generation while checking changed storage generation and work revision.
It also checks rejection of the already completed delivery claim and stale operator versions.
The failed run remains in [behavior-first.log](evidence/rom-0.0.2/task6/behavior-first.log).
This correction is not reported as a product RED/GREEN fix.

The fixture helpers were split into file lifecycle, native storage, application model and managed identity modules.
The test entrypoint and module facades contain declarations and exports only.
Existing signing and subprocess implementations are imported by path into this unpublished repository harness.
Their implementations were not copied or changed.

## Acceptance limits

These cases close the direct native query and seeded operator schema-migration gaps.
They also extend real managed identity revocation and maintenance ordering to both stores.
They do not complete Task 6 by themselves.

Actual human-provider login, authorization-code redemption, browser session/CSRF behavior and opaque cookie handling require the maintained Studio host.
Active authentication and upload interruption require actual serving-process SIGINT/SIGTERM and reopen journeys.
A forced process exit, graceful signal, transport failure and storage maintenance remain separate outcomes.
The later integrated provider journey must preserve current authorization and establish identity again after maintenance.
These native fixtures must not be cited as that actual-provider or browser evidence.
