# Technology fit review

Date: 2026-10-02. This review inspected retained source, implementer assessments and current primary documentation. It did not rerun benchmarks or tests. It does not speak as the agents who implemented the experiments. Reported execution results come from the linked research and retained assessments. The recommendations below are this review's judgment.

The technology direction is sound for a Rust resource framework. Keep the selected architecture and move to one integrated typed library slice. The biggest uncertainty is whether independently demonstrated guarantees compose through that interface. Choosing more dependencies will not answer that question.

## Concrete authoring friction

The [library example](https://github.com/pmikstacki/ROM/blob/prototype/library-slice/prototypes/library-slice/examples/app.rs) is easy to follow because registration, mutation and subscription are colocated. However, its business function writes `data["done"]`, queries use `"done"`, and actions use a positional string/name/revision/JSON call. A misspelled field or misunderstood argument is not the typed experience the project intends. Typed field/action handles and ordinary typed state/input should be acceptance criteria, not future polish.

The [Bon source](https://github.com/pmikstacki/ROM/blob/prototype/authoring-builders/prototypes/authoring-builders/src/bon_style.rs) keeps the caller small while its helper handles generated state bounds. That is an acceptable responsibility split. Its `Option<Option<String>>` distinguishes absence/null/value but exposes awkward vocabulary. ROM needs deliberate patch operations and matching codecs. Builder construction alone does not establish transport semantics.

The [renamed derive fixture](https://github.com/pmikstacki/ROM/blob/prototype/derive-contract/prototypes/derive-contract/fixtures/renamed/src/lib.rs) requires an explicit crate-path override. This works, but automatic discovery and facade reexports deserve integration coverage. Separately, the [Salsa source](https://github.com/pmikstacki/ROM/blob/prototype/salsa-reads/prototypes/salsa-reads/src/lib.rs) repeats Task fields as TaskFact and manually reconciles snapshots. Exposing that work to application authors would undermine the single Resource premise.

## Next acceptance boundary

Build one external consumer that declares a resource, adds a typed action, observes a filtered result and changes permissions through the proposed public facade. Combine cancellation after admission, uncertain commit/retry, stale buffered authorization and missing/null/value decoding in that same implementation. Verify bounded lifecycle behavior and both manual/derived registration paths. Then exercise the HTTP extension against it.

The source was reviewable because ordinary traits, examples and explicit negative controls made responsibilities visible. That is evidence about this review experience, not a human usability study. Production MSRV, dependency compatibility, query breadth, retention and deployment topology remain decisions. The [readiness assessment](core-implementation-readiness.md) records their scope impact. A human author walkthrough and an integrated consumer are now more informative than another unrelated crate comparison.
