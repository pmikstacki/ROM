# Built-in temporary cache and command deduplication

Research date: 2026-10-02. This is primary-documentation and source research, not a performance ranking or production adoption. It follows [Optional pre-persistence deduplication](../../openspec/changes/design-capability-adapters/design.md#optional-pre-persistence-deduplication). The cache is a ROM implementation detail with capacity/expiry controls, not another replaceable provider contract. Executed trials belong in the separate prototype results.

## Candidate libraries

| Candidate checked | Documented behavior | ROM assessment |
| --- | --- | --- |
| Moka 0.12.16, `future` | Concurrent memory cache, coalesced initialization, weighted capacity, TTL/TTI and per-entry expiry. Capacity is explicitly best effort. | Strong feature fit for confirmed receipts; assess against the simpler alternative. [API](https://docs.rs/moka/0.12.16/moka/future/struct.Cache.html) |
| quick_cache 0.7.0 | Sharded concurrent cache, user weights, sync/async insertion guards. Its exposed options do not provide built-in TTL. | Viable receipt cache with ROM-owned expiry checks; native guards do not remove lifecycle work. [API](https://docs.rs/quick_cache/0.7.0/quick_cache/sync/struct.Cache.html), [options source](https://github.com/arthurprs/quick-cache/blob/v0.7.0/src/options.rs) |
| Foyer 0.22.6 | Hybrid cache integrates memory and disk; `contains` may report an enqueued entry before disk flushing, without a guarantee. | Additional disk lifecycle is unjustified for this small temporary index; it is not ROM's atomic receipt authority. [HybridCache](https://docs.rs/foyer/0.22.6/foyer/struct.HybridCache.html) |
| redb 4.3.0 | Embedded transactional key-value database with copy-on-write B+trees, MVCC and crash safety. | Possible durable storage implementation, a different role from disposable cache storage. A separate redb receipt database would not automatically commit atomically with another backend's resource writes. [redb](https://docs.rs/redb/4.3.0/redb/) |
| Salsa 0.28.5 | Incremental computations memoize results and track dependencies across revisions. | Suitable for dependency-driven derived computation, not an interchangeable command receipt cache. Reusing a pure query result and arbitrating an effectful operation have different semantics. [Salsa](https://docs.rs/salsa/0.28.5/salsa/) |

Moka's `try_get_with` inserts successful values, shares an initializer error with participating callers of the same error type, and does not cache that error. A panicking initializer panics its caller; remaining callers can run another initializer. Its source also handles an aborted enclosing future by removing the waiter and allowing another initialization attempt. Cleanup therefore does **not** mean the original database operation was rolled back or remains supervised. [Moka API](https://docs.rs/moka/0.12.16/moka/future/struct.Cache.html), [initializer source](https://github.com/moka-rs/moka/blob/v0.12.16/src/future/value_initializer.rs)

quick_cache's `get_or_insert_async` awaits the caller's future while owning a placeholder guard. On error, cancellation or unwinding, the unfilled guard is dropped; it wakes another waiter or removes the placeholder. Errors are not a persistent negative cache, and successive waiters can each try their own initializer. These are source-derived cancellation conclusions, not locally measured tests. [Loader source](https://github.com/arthurprs/quick-cache/blob/v0.7.0/src/sync.rs#L678), [guard cleanup](https://github.com/arthurprs/quick-cache/blob/v0.7.0/src/sync_placeholder.rs#L455)

## Required ROM semantics

The following are proposed ROM acceptance requirements, derived from the existing persistence and authorization designs:

1. **Identity before sharing.** Index by trusted namespace/storage generation, tenant or authorization domain, resource/action and explicit command identity. Store and compare a versioned canonical request fingerprint, including operation arguments and relevant preconditions, before joining. A changed request under one command identity is a mismatch, not another operation. Payload equality across distinct command identities must never merge intended actions. Bound input before canonicalization; use unambiguous field encoding and a collision-resistant digest, not a hash-table bucket hash. Include principal identity where required by the command scope, rather than treating possession of an identity as permission.
2. **Authorize each caller and each disclosure.** Admission and result delivery both use current access policy, including cached hits. Resource ownership, field policy or deletion may change on another instance. A test permission boolean does not establish production policy freshness. Some policies require authoritative database reads even on a cache hit; eliminating receipt arbitration calls does not establish elimination of all database calls. Cache minimal safe receipts, not credentials or previously authorized response bodies. [Auth design](../../openspec/changes/design-provider-neutral-auth/design.md)
3. **Own submitted work independently.** Keep bounded in-flight jobs separately from evictable completed entries. Caller disconnect or waiter timeout must not cancel a submitted commit. Eviction must not discard supervision. Bound unique jobs, queued admission, total waiters, waiter bytes and deadlines separately. A worker panic must release bookkeeping and wake waiters with an honest outcome; once submission could have occurred, that outcome may be `Unknown`. Shutdown must drain or preserve recoverable uncertainty.
4. **Enforce an absolute validity horizon.** Every receipt has a deadline no later than durable identity retention and applicable generation validity. Rehydrating or repeatedly reading it cannot renew that horizon. Check validity at disclosure even when eviction is delayed. Moka TTL starts at insertion; TTI extends on access, so TTI alone cannot implement this rule. Its per-entry expiry can assist; quick_cache needs explicit checks and safe stale-entry removal. [Moka expiry builder](https://docs.rs/moka/0.12.16/moka/future/struct.CacheBuilder.html)
5. **Treat weight as accounting, not strict memory isolation.** Include keys, owned buffers, retained `Arc` values and metadata when estimating weight. quick_cache explicitly excludes key/value heap allocations from `memory_used`; shard allocation also matters. Neither an entry limit nor a chosen weight function caps all task, waiter or allocator memory. Enforce separate admission and payload bounds and measure actual peak memory. [quick_cache memory accounting](https://docs.rs/quick_cache/0.7.0/quick_cache/sync/struct.Cache.html#method.memory_used)
6. **Keep the durable guard authoritative.** Eviction, restart and independent hosts can all miss simultaneously. Every write still atomically arbitrates scoped identity/fingerprint with state, revision, receipt and events. Cache only confirmed outcomes initially. A missing receipt, timeout, cancellation, panic or lost acknowledgment is not a definite failure. Negative caching requires a separately specified stable rejection and freshness policy; `Unknown` must remain resolvable through the original identity. [Persistence design](../../openspec/changes/design-capability-adapters/design.md#persistence-protocol)

## Dependency first; vendoring only for a concrete need

Recommend ordinary private Cargo dependencies with locked probe versions. Moka declares Rust 1.71.1 and license expression `(MIT OR Apache-2.0) AND Apache-2.0`; its read LICENSE/NOTICE files identify two Apache-only Caffeine-derived modules. quick_cache declares Rust 1.85 and MIT in its manifest; that metadata is not a complete license-file or transitive-dependency audit. Check the actual selected feature graph, advisories, licenses and ROM's compiler target before adoption. [Moka manifest](https://github.com/moka-rs/moka/blob/v0.12.16/Cargo.toml), [licensing notice](https://github.com/moka-rs/moka/blob/v0.12.16/NOTICE), [quick_cache manifest](https://github.com/arthurprs/quick-cache/blob/v0.7.0/Cargo.toml)

If offline or hermetic distribution later requires vendoring, use Cargo's vendor/source-replacement mechanism and retain upstream provenance, notices and an update process. A maintained source snapshot still needs dependency upgrades and regression checks. Copying selected implementation code into ROM creates fork maintenance without demonstrating a current benefit. [Cargo vendor](https://doc.rust-lang.org/cargo/commands/cargo-vendor.html)

## Narrow adoption gate

Compare durable-only, supervised single-flight-only, single-flight plus Moka, and single-flight plus quick_cache with identical semantics. First prove identity mismatch, distinct command identities, generation/tenant isolation, current authorization, deadline expiry, eviction under load, leader/follower cancellation, panic cleanup, unknown-after-commit recovery and independent-instance arbitration. Count actual durable calls and committed bundles; one committed effect alone does not prove duplicate work was avoided.

Then measure unique requests, warm replay, overlapping bursts, mixed workloads, payload hashing and churn. Report distributions, throughput, hit/join/rejection rates and peak memory over repeated release runs. Separate database locking and connection serialization from cache contention; compare equal canonicalization/hashing, ownership, payloads and capacity. Include allocator retention, cache warmup, maintenance and SQL durability settings. Synchronous SQL on a runtime worker, a global connection mutex, a tiny hot key set, or hashing omitted from only one path can dominate the comparison. Define an acceptable unique-request regression budget before interpreting results. Adopt only when measured duplicate savings justify the added lifecycle complexity; these sources alone select no performance winner.
