# ROM 0.0.2 Studio Implementation Plan

> **For agentic workers:** Use superpowers:subagent-driven-development or superpowers:executing-plans to implement this plan task-by-task. The owner authorized autonomous execution; no additional approval handoff is required.

**Goal:** Release working generic Studio and close selected integrated resilience gaps in ROM 0.0.2.

**Architecture:** Static Svelte assets use a framework-independent client over the existing generic HTTP binding. An optional Rust host supplies assets and verified browser sessions. All mutations, authorization, queries, and persistence remain in the shared Resource pipeline.

**Tech Stack:** Rust 1.99, Tokio/Rayon, SQLite/redb, Svelte 5, Vite 8, selected shadcn-svelte source, Bits UI, Tailwind 4, TypeScript, Playwright.

**Spec:** [Studio design](../specs/2026-10-03-rom-0.0.2-studio-design.md) and [OpenSpec requirements](../../../openspec/changes/release-rom-0-0-2-studio/specs/studio-release/spec.md).

## Global Constraints

- Resource is the sole domain entity. Actions request mutations; events describe committed transitions.
- The owner selected the release identifier `0.0.2`.
- Retain the single-owner native profile, CLI, Tokio/Rayon execution, and adapter-independent core.
- Rust source APIs remain experimental. Process-exit recovery does not certify machine power-loss durability.
- Keep `lib.rs` and `mod.rs` as module facades. Put implementation and tests in named modules.
- Use existing persistent ROM build targets. Do not duplicate large Cargo caches or remove retained evidence.
- Use local release gates. GitHub hosts source only; Actions remains disabled.
- Preserve prior release archives, package fixtures, and evidence. Update current versions with explicit compatibility notes.
- Record selected upstream component URLs, license, content hashes, and local modifications.
- Pin tested package versions and lockfiles. Documentation review alone is not executable compatibility evidence.

## Review Focus

- Boundary integers and omitted/null/removal intents must round trip through actual HTTP, not a mock Number codec.
- Late responses and streams from a prior session must not disclose data in the next session.
- Lost responses after commit must retain the exact request identity and preserve current authorization on recovery.
- Provider configuration must not grant unapproved network authority or turn browser data into a trusted Actor.
- Extracted deployments must preserve base paths, session protection, asset inventory, and stream behavior after restart.

## Ownership and order

Use an isolated release worktree before product implementation. One coordinator owns integration and version changes.
Assign one writer per task's files. Independent reviewers may read all files but must not edit another writer's scope.
Tasks 2, 3, and 4 may proceed independently after Task 1 freezes their interfaces.
Task 5 consumes those interfaces. Task 6 follows integration. Task 7 follows complete acceptance.
Each task includes a failure-first regression, implementation, focused checks, and review before integration.

### Accepted codec ordering deviation

Original Task 2.4 wording:

> Implement a lossless codec using a verified dependency or narrowly scoped parser; benchmark against the wire fixtures before adoption.

The before-adoption order was not met. The coordinator accepts this timing deviation after independent review of the retained native-fixture benchmark. The active checkbox now requires the executed benchmark and an explicit selection/timing record. Correctness obligations remain unchanged. The existing codec stays because its bounded lossless contract is required; these small timing samples do not justify replacing it.

Before adopting any replacement, run a comparative benchmark on declared workloads and preserve all codec correctness guarantees. Final complete-producer acceptance remains required. This deviation changes only the historical ordering requirement, not the Resource model or release scope.
