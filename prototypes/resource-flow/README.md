# Resource flow: disposable backend prototype

**Question:** can unrelated resource kinds obtain fields, generic persistence/actions, HTTP CRUD, committed subscriptions and reactions from one declaration, with a third kind added by declaration alone?

**Observed answer:** yes for the deliberately small contract implemented here. Twelve executable integration probes passed on Rust 1.82 and Node 22. The third resource adds three declaration lines and no repository, route, handler or stream implementation. This is experimental evidence about a shared path, not a finished ROM framework, final macro API or production database recommendation.

This prototype and the execution-contract prototype test complementary layers. This one tests authoring and end-to-end resource flow. Their results do not establish that one prototype replaces the other.

## Run

From this directory inside the provided native NixOS development container:

```sh
./verify
```

One command from the host:

```sh
nixos-container run rom-dev -- sh -lc 'cd /workspace/ROM/.worktrees/resource-flow/prototypes/resource-flow && ./verify'
```

The command builds from `Cargo.lock`, starts real loopback servers on ephemeral ports, drives HTTP and SSE using Node's built-in `fetch`, injects a transaction failure and a reaction crash, suppresses wake-up hints, kills/restarts the server and removes its scratch database. No frontend, Docker, external service or Rust toolchain installation is required.

To serve manually:

```sh
nixos-container run rom-dev -- sh -lc 'cd /workspace/ROM/.worktrees/resource-flow/prototypes/resource-flow && ./serve'
```

The address is `http://127.0.0.1:7310` **inside the container's network namespace**. The database is `PROTOTYPE-wipe-me.sqlite` in this directory. `PORT` and `PROTOTYPE_DB` override these defaults. `serve` and `verify` are also usable directly in any compatible Rust/Node environment. Stop the manual server before removing its database/WAL files.

For example, from the same namespace:

```sh
curl -H 'x-principal: alice' -H 'content-type: application/json' \
  -d '{"action_id":"create-1","expected_revision":0,"input":{"code":"ROOF","reading":12.5}}' \
  http://127.0.0.1:7310/resources/sensor/roof

curl -N -H 'x-principal: alice' http://127.0.0.1:7310/events?after=0
```

## What a resource author writes

All three resources are in `src/declarations.rs`, inside one `resources!` invocation. The registry is generated by the same macro invocation; there is no second registration list.

```rust
sensor { code: UpperCode, reading: f64 }
actions {}
reactions [];
```

That third kind costs **three nonblank declaration lines**. The task kind also costs three; it adds a one-line literal `complete` action. The thermostat declaration costs seven nonblank lines including its literal `disable` action and a reaction definition.

For **each additional kind**, the number of hand-written persistence repositories, CRUD functions, HTTP routes, HTTP handlers and stream functions is **zero**. The generic runtime has no match on resource kind. All kinds use `/resources/:kind/:id`, `/resources/:kind/:id/actions/:action`, the same SQL tables and `/events`.

The optional `UpperCode` semantic field implements the ordinary Rust `FieldType` trait once. The declaration selects it directly; neither runtime nor HTTP knows about this extension. Its uppercase/length behavior is validated by a probe. Other domain-specific behavior still has to be authored: fields, action patch contents, reaction conditions and target payloads. The prototype supports literal patch actions and a small declarative reaction only; arbitrary typed async business handlers remain unproven.

The macro currently creates **typed field descriptors**, not Rust resource structs or typed field accessors. Runtime documents are validated `serde_json::Value` objects. This choice minimizes experimental code while exposing the authoring boundary honestly.

## Shared execution path

```text
resource declaration -> descriptor registry -> generic Axum route
  -> bounded admission -> field validation on a bounded Rayon pool
  -> blocking database task -> SQLite immediate transaction
       load + owner check + scoped receipt lookup + expected revision
       apply mutation + validate merged document
       write resource + committed event + idempotency receipt
       commit
  -> reply containing resource, revision and event ID
  -> best-effort notification hint
       SSE: durable journal replay from cursor
       reaction worker: durable progress -> same generic action path
```

Tokio hosts I/O, the reaction loop, SSE and blocking-work submission. Two Rayon threads demonstrate a CPU-extension boundary; these tiny validators do **not** justify a pool on performance grounds. CPU and database admission each reject excess submissions rather than spawn unlimited waiting work; their permits remain owned by the work until it actually finishes. This does not bound all HTTP connections or SSE subscribers.

SQLite uses generic `resources`, `events`, `receipts` and `reaction_progress` tables. It is a scratch probe choice, not a final ROM storage selection. No schema table is created per kind.

| Endpoint | Behavior |
| --- | --- |
| `GET /schema` | Descriptor registry for every declared kind |
| `POST /resources/:kind/:id` | Create through generic action transaction |
| `GET /resources/:kind` | Owner-scoped list |
| `GET /resources/:kind/:id` | Owner-scoped read |
| `PATCH /resources/:kind/:id` | Top-level field replacement patch |
| `DELETE /resources/:kind/:id` | Revisioned tombstone through same transaction |
| `POST /resources/:kind/:id/actions/:action` | Declared literal patch action through same transaction |
| `GET /events?after=N` | Owner-scoped SSE; committed snapshots, durable sequence IDs |
| `GET /journal?after=N` | Up to 128 owner-scoped committed events for diagnostics/replay |

Mutation bodies contain `action_id`, `expected_revision` and `input`. All declared fields must be present on creation; `Option<T>` permits an explicit null. Patch omission preserves the old value; false replaces true; nullable null remains null. This is not JSON Merge Patch: null does not remove a field. Unknown fields and wrong types are rejected.

No-op actions keep the current revision and create no event, but still persist their receipt. Expected revision is checked before deciding no-op. Receipt identity includes principal, resource kind/ID, verb and caller action ID; the complete request must also match. Same-key retries return the stored outcome even after later state changes. Tombstones retain identity and prevent accidental ID reuse.

SSE reads committed journal rows first, then waits for an in-memory hint or a short periodic retry. `Last-Event-ID` overrides the query cursor. Hints are never the source of truth; a fresh process can replay with no remembered hints. These are event subscriptions, **not automatically maintained filtered live queries**.

The sample reaction reads update events whose snapshot has `enabled=false` and creates a task resource using the original owner's historical scope and the same action executor. This is not a service principal or a current-policy authorization evaluation. It matches every qualifying update snapshot, not only a true-to-false edge. Deterministic reaction action IDs make retries idempotent. Progress is checkpointed after successful target action completion; it can resume from earlier events after restart.

## Actual verification, 2026-10-02

The executable `probes.mjs` checks:

1. Registry discovery and generic create/read/list for all three declarations.
2. Custom semantic field rejection and unknown-field rejection with no resource insertion.
3. False and zero versus omitted versus explicit null; null rejection on a boolean.
4. No-op revision/event behavior, exact same-key retry, changed-input rejection.
5. Declared action -> committed SQLite event -> live SSE; mutation retry.
6. Two concurrent HTTP mutations with one expected revision: exactly one success and one conflict.
7. Failure injected after resource/event/receipt SQL but before commit: resource and journal unchanged; the same-key retry commits, establishing receipt rollback too.
8. Owner checks on read/mutation/receipt access, owner-scoped lists/journal, missing-principal rejection.
9. SIGKILL/restart, persisted resource, SSE replay via `Last-Event-ID`, plus termination immediately after reaction target commit and before cursor advancement. Restart replays that action without duplicating its event and catches up later reactions.
10. Third kind's delete/tombstone event and idempotent deletion retry.
11. Suppressed in-memory notification hint: SSE still discovers the committed event by polling the journal.
12. The maximum accepted source ID (128 bytes), followed by another source: both reactions complete with bounded target IDs.

The initial empty-server run failed at `/schema` with HTTP 501 as expected. An initial dependency resolution failed because a new transitive `hyper-util` manifest required Cargo edition-2024 support. Explicit compatible dependency pins resolved this on the existing Rust 1.82 toolchain; no toolchain upgrade was needed. The first implemented run passed ten probes. Independent review then identified an accepted source ID that overflowed the derived target-ID limit and stalled the reaction cursor. The added regression failed (zero target events instead of two), then passed after replacing concatenated source IDs with a bounded declaration namespace and durable journal sequence. Nullable metadata was also added after a failing schema assertion. The final run passed all twelve probes, `cargo fmt --check`, and `cargo clippy --locked -- -D warnings`.

## Implementer assessment

**Preferred implementation pattern:** a validated descriptor registry plus a single action transaction is the useful foundation demonstrated here. Adding unrelated kinds changed only declarations. Per-kind repositories/controllers would repeat this routing and storage policy; that is an architectural comparison, not a benchmark against a second implementation.

**Durable journal over notification authority:** live delivery, intentionally suppressed hints and replay after loss of process memory were exercised. The post-reaction-commit/pre-checkpoint crash was also exercised; replay used the stored action receipt and did not duplicate target events. This supports keeping notifications as wake-ups and persistent event IDs as the recovery contract. We did not implement or benchmark a competing notification-only design.

**Useful patterns:** one registry drives all adapters; absence is represented separately from false/null; no-op is explicit; resource/event/receipt updates share one transaction; observers publish only committed facts; reaction side effects reuse the ordinary action path; CPU/database work retains its admission permit after caller disconnection.

**JSON and SQLite tradeoffs:** generic validated JSON made declaration-only kinds easy and prevented per-kind table/repository proliferation. It does not provide compile-time typed resource mutation or final indexing/query/migration semantics. SQLite made rollback and restart probes inexpensive; one connection plus a mutex serializes this host's database work. These probes establish neither multi-process database concurrency behavior nor throughput superiority.

## Explicit limits

- `x-principal` is a caller-claimed identity stub, not authentication. Local callers can claim another identity. No external access should be enabled.
- The server is a prototype binary, not a released embeddable library API. Its modules demonstrate boundaries; reusable public API, dependency features and transport-free embedding still need a separate experiment.
- No authorization policies, field ownership modes, secret redaction, reference integrity, schema versioning, migrations, rich query operators or production error sanitization. Events contain full snapshots.
- Metadata publishes type names and nullability, but no complete JSON Schema or detailed custom-type constraints. Validation knows the custom acceptance rule.
- Named actions are literal patches. Reactions use one fixed durable cursor and simple predicates. No configurable user callbacks, external side effects, dead-lettering, leases, multi-worker claiming, poison-event recovery or reaction graph cycle analysis.
- Reaction target identity uses a bounded, startup-validated unique declaration namespace plus journal sequence. Collisions with manually authored IDs or other permanent reaction errors can still stall the single worker; this is not a production delivery protocol.
- Hard restart was tested after completed commits and between a reaction action commit and cursor update. SQL rollback was tested after state, event and receipt writes. A crash inside SQLite commit itself was not injected.
- Same-process concurrent HTTP requests were tested; independent processes/connections and database adapter portability were not.
- No evidence about performance, saturation behavior, graceful shutdown, authorization changes during retries, durable admission, security isolation or exactly-once external effects.
- Fault injection requires `PROTOTYPE_FAULTS=1`: the header `x-prototype-fail: after-event` fails after all three writes; `PROTOTYPE_DROP_HINTS=1` suppresses hints; `PROTOTYPE_REACTION_CRASH_AFTER_COMMIT=1` exits with code 86 after the target action commits. All are off for ordinary serving.
- No frontend and no automatic filtered live-query subscription. These remain separate experiments.
